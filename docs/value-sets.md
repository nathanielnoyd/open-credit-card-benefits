# Value sets

What a perk or a point is worth is an opinion, and the most personal number in OCCB: a $400 Resy credit is worth close to $400 to someone who eats at Resy restaurants every month, and nothing to someone who doesn't. So OCCB doesn't say what perks are worth. The catalog holds facts; the spec defines how values are written down and how a calculator combines them with the facts. The values themselves come from whoever builds the calculator, a publisher it trusts, or the user.

A value set is that input. A calculator passes one to valuation (`valueWallet(catalog, wallet, { asOf, values })`), and the user's own values override it.

## What goes in a value set

A value set has a `scope` (usually `publisher`), a `source`, an `as_of` date and a `method`, plus:

- **Perk values** (`benefit_values`), keyed by benefit ID, each with:
  - **a typical value**: what a typical holder of that card would prepay for the perk on the fee date (spec section 12), as `personal_value` in dollars or, for a credit, `usage_probability`, a share of face value. A share is a derived value: the engine deducts the earn given up by putting the credit's purchases on that card, using the holder's actual wallet, and discounts it across the year. A dollar value is already a prepaid amount.
  - **a range**: `low`, what the perk is worth to the holder who gets least from it (usually nothing), and `high`, to the one who gets most (usually face value). The range tells an app how much the answer depends on the user and which questions to ask.
  - **a note**: the reason for the typical value, a sentence an app can show next to it.
- **Points valuations** (`valuations`), in cents per point by currency, in the snapshot format of spec section 11.
- **Finance assumptions** (`finance`): the discount rate, expected devaluation by currency and how long points are held before redemption (spec section 12). A user's own `finance` overrides them.

A value never includes overlap with other cards; the engine works that out for each wallet (spec section 6). So a value is a card's standalone value, even when the same perk is on many cards.

## Without a value set

Valuation still runs, on facts alone: a credit counts at its face value (less the earn its purchases give up), a perk with no face value at zero, points at their currency's fixed rate or 1 cent, and nothing is discounted or devalued. The result lists each of those under `unvalued` (`benefits`, `currencies` and `finance`), so the app can ask the user, or fill them from a value set.

## How users answer

The user's own values always win, in this order: a value for the specific benefit (`benefit_values`), then an answer for what it grants (`entitlement_values`, such as `credit:resy`, which covers every card's Resy credit at once), then the app's value set, then face value. One answer per perk type is usually enough: a person who doesn't use Resy says so once, not once per card.

## The example value set

`examples/value-sets` holds one example, generated by `node examples/value-sets/generate.mjs` (`--check` lists perks no rule covers). It is one publisher's opinions, written to show the format and to give the example app something to run on, not a recommendation. It values perks at what a typical holder would prepay, which is lower than what they end up using: people discount an uncertain future credit for the risk of not using it and the effort of tracking it, and a credit is worth face value only when it replaces spending they'd do anyway. It errs low on purpose, since an app that asks the user corrects a low value but an overvalued perk makes people pay fees for value they won't get.

| Perk | Typical prepay value | Range |
| --- | --- | --- |
| Statement credit | Face value × a prepay share: 0.85 near-cash (any travel, automatic); 0.6 a bill most people already pay; 0.5 any airline purchase or portal travel; 0.35 a broad merchant with monthly expiry; 0.25 worth face to regular users of the merchant; 0.1–0.2 a specific merchant, channel, stay or minimum; 0.05 one merchant most holders don't use; 0–0.02 a niche merchant or premium membership | 0 to face value |
| Membership the card pays for (Apple, DashPass, Uber One, Walmart+, Instacart+) | 0.1–0.2 of its price: worth it only to people who would subscribe anyway | 0 to price |
| The card's main lounge network | $100 on a bank card, where lounges are one perk among many | $0 to $600 |
| An airline card's own club (United Club, Sky Club, Admirals Club, Alaska lounges) | $300: the reason most holders have the card | $0 to $750 |
| One-time lounge passes (8 or fewer) | $15 a pass | $0 to $50 a pass |
| Other lounge networks on the same card | $0–$25: a traveler uses one lounge per visit, so a second network adds little | $0 to $100–$500 |
| Elite status from the card | $0–$25 | $0 to $50–$300 |
| Free checked bag on the cobrand airline | $40 for the first bag, $10 for a second | $0 to $300 |
| Priority boarding, in-flight discounts, same-day changes | $2–$5 | $0 to $50–$100 |
| Companion certificate | $75–$125, discounted for restrictions and the chance it goes unused | $0 to $400–$600 |
| Status credits, award discounts, earn boosts counted elsewhere | $0–$5: worth something only to status chasers and frequent award bookers | $0 to $100–$300 |
| Protections | $10 for trip delay, cancellation, rental and phone; $0 for the rest: claims are rare | $0 to $25–$150 |
| No foreign transaction fee | $5 | $0 to $300 |
| Free night certificate | $100–$200 by its points cap, allowing for the chance it expires unused | $0 to 3 times that |

Spend milestones and spend-unlocked perks keep their own values, since the engine counts them only when the user routes the spend. Anniversary points are valued from the currency. Redemption perks such as Points Boost count only when the user values them. The rules cover all 950 perks on the cards that aren't variants (variants take their base card's values); perk types found across the catalog were classified by subagents against these rules and reviewed, and the assignments are in the generator's `ASSIGN`, `FIXED` and `BY_BENEFIT` tables. The points valuations are dated benchmarks from published reviews, with their sources. Its finance assumptions are a 4.5% discount rate, points held 18 months, and 6% a year expected devaluation for every currency that can devalue.
